**Phase 12 in one paragraph:** the new `remediation/` package (plus `scripts/run_remediation_plan.py`) produces **advisory remediation proposals** and executes nothing. It takes the verified Phase 11D `GroundedContext` (observed evidence, Phase 9 hypotheses, retrieved passages with provenance), the Phase 11D answer for that context and a new, separate category of **configuration facts**, and keeps all four apart: proposals cite `observed_evidence_ids`, `hypothesis_ids`, `reference_ids` (chunk ids) and `configuration_fact_ids` in different fields, and validation rejects an id in the wrong field. A passage may be used only if the accepted, re-validated Phase 11D answer labelled it `relevant` (`not_relevant`, `unclear` and unlabelled passages are excluded and never shown to the planner). If there is no observed evidence, no reference material, no validated relevance assessment or no relevant passage, the planner does **not call the model** and returns an explicit insufficient-evidence plan. The model's response is strictly parsed and then validated (fabricated ids, category mixing, excluded passages, hypotheses presented as confirmed, claims of compromise or of remediation success, invented CVE/CWE ids, invented paths and commands, missing configuration admissions, overconfident ratings); any issue rejects the whole plan (no repair, no retry, no partial plan). Priority is **not** supplied by the model: a documented ordinal rule computes it, and the output says it is not a risk score. **Tests used mocked `LLMClient` responses only; no live Groq call was made for Phase 12.** 248 new tests; full suite **1996 passed** (was 1748). ## 1. Project overview

AutoShield is an evidence-grounded AI cybersecurity system for **post-incident** work. Its intended closed loop:

1. Reproduce a controlled incident in an isolated Docker cyber range.
2. Collect, normalize and extract forensic evidence, with provenance.
3. Build an attack graph; reconstruct the incident; form a root-cause hypothesis.
4. Retrieve security knowledge and plan evidence-grounded remediation.
5. Validate the remediation by re-testing the original attack objective inside the authorized lab.
6. Judge the remediation using real validation evidence; explain the decision; estimate residual risk.
7. Present real pipeline outputs in a dashboard.

Principles (from `PROJECT_SPEC.md`): no evidence, no claim; separate observed, configured and inferred; never leak ground truth to models; correlation is not attribution; validation success is not a security guarantee.

Phases 0–9 cover steps 1–3 (partially, see section 3). Step 4 is **partly started**: Phase 10 (knowledge base foundation) is in progress and Phase 11 has a keyword-retrieval contract and baseline (Milestone 11A, section 3.5). *(Updated for Milestone 11D, section 3.9: the Phase 8/9 JSON output now feeds FTS5 v1 retrieval and a citation-validated answer step, tested with mocked model responses only; semantic retrieval exists but is experimental and unused by it. There is still no remediation planning.)* *(Update, Phase 12, section 3.10: advisory remediation planning now exists, built on the 11D context and tested with mocked model responses only; nothing is executed.)* Steps 5–7 (Phases 13–16 and 20) are **not started**. *(Update, Phase 13A, section 3.11: an offline validation contract, scope policy and report exist for step 5; no validation has been run and none is claimed.)*

**`KnowledgeStore` public capabilities (high level):** `KnowledgeStore(path)` (file path or `":memory:"`, no default path, context manager); `ingest_document(document, chunks=None, config=None)` returning an `IngestResult` (`created` / `unchanged` / `updated` plus flags for content, metadata, provenance, config and chunk replacement); `get_document`, `get_chunks` (numeric ordinal order), `has_document`, `list_doc_ids`, `count_documents`, `count_chunks`, `delete_document`; `search(query, limit=10)` returning `SearchHit(chunk, bm25)`; `ChunkingConfig(max_chars, overlap_chars, chunker_version)`. **Design facts reviewed and confirmed in code:**
- Tables: `store_meta`, `documents`, `chunks`, `chunks_fts` (FTS5, derived data). Documents and chunks are stored as full JSON plus cross-checked identity/hash columns; the **complete original document is always kept**.
- Every write is one explicit `BEGIN IMMEDIATE … COMMIT`; any error rolls back document row, chunks, ingestion state and FTS rows together. Connection uses `isolation_level=None` so Python never commits implicitly. Reads that span tables use one read transaction.
- Per-document ingestion state records chunker version, `max_chars`, `overlap_chars`, normalization version, chunk count and a digest of all chunks. Re-ingesting an unchanged document writes nothing (tested with insert/update/delete triggers).
- Loading goes through `model_validate_json` (never `model_construct`) plus `contains_chunk()`, ordinal/count/chunker-version/digest checks; any disagreement raises `StoreCorruptionError`.
- Compatibility markers in `store_meta`: store schema version `"1"`, `NORMALIZATION_VERSION = "normalize-text-v1"` (manually maintained, defined in the store because `schema.py` has no such constant), document schema version, document-hash version. A mismatch raises `IncompatibleStoreError`; there is no migration (rebuild from sources). A test pins a fingerprint of `normalize_text` output so behaviour drift is noticed.
- FTS5 support is probed on every open; if missing, `FTS5UnavailableError` is raised (no fallback search). SQLite in the venv is 3.42.0 with FTS5.
- All SQL values, including search queries and IDs, are bound parameters.

**Acceptance review result:** Milestone 3 **accepted** (earlier session). No correctness defect was found in the review. See section 5 for the test results and section 6 for the limitations that later milestones must respect.

**Milestone 4A data flow and public API (`ingestion` package) [Verified by code reading and tests]:**
```
local JSON file --load_documents(path)--> list[SourceDocument]   (schema validation; first bad record raises)
                --ingest_documents(documents, store, config)-->
                      pre-flight (types, re-validation, duplicates, chunking)   no DB access
                      -> per document, ascending doc_id: KnowledgeStore.ingest_document(document, chunks, config)
                --> IngestionSummary(config, results, duplicates_skipped)
```
- `ingestion` exports `load_documents`, `ingest_documents`, `IngestionSummary` (`.created/.updated/.unchanged` doc-ID tuples, `.total`, `.results` = the store's own `IngestResult`s, `.duplicates_skipped`, `.config`), `FORMAT_ID`, and the errors `LocalJsonError`, `IngestionError`, `InvalidDocumentInputError`, `DuplicateDocumentError`, `BatchIngestionError`.
- **Loader policy:** strict. Unreadable file, bad UTF-8, malformed JSON, duplicate JSON keys, wrong top level or `format`, unknown top-level keys, non-object or schema-invalid records all raise `LocalJsonError` naming the path and `documents[<index>]` (underlying exception as `__cause__`; document content is not echoed). Nothing is skipped or returned partially. Provenance, URLs, licences and timestamps are taken from the record verbatim and are never invented; missing required fields are errors. A repeated `doc_id` within one file is an error. An empty `documents` list is valid and returns `[]`.
- **Pipeline duplicate policy:** inputs with the same `doc_id` that are fully identical (`==`, including provenance) are collapsed once and listed in `duplicates_skipped`; if they differ in any way (even provenance only) `DuplicateDocumentError` is raised **before any write**. Nothing is merged and input order never decides a winner.
- **Pipeline order and failure policy:** documents are written in ascending `doc_id` order regardless of input order. Everything checkable without the database (item types, re-validation through the schema, duplicates, chunking) happens before the first write. Each document is its **own store transaction**; the batch is **not atomic**. A store failure on document N raises `BatchIngestionError` (`failed_doc_id`, `completed` summary, `__cause__`); earlier documents stay committed, N is rolled back, later ones are not attempted. Re-running is safe: finished documents return `unchanged`.
- Empty input returns an empty summary and writes nothing. Change detection, idempotency and rollback remain entirely the store's (the pipeline adds no second implementation).

**Integration status:** nothing outside `tests/`, `scripts/ingest_mitre_corpus.py`, `scripts/run_retrieval_baseline.py` and the `knowledge/`, `ingestion/` and `retrieval/` packages imports `knowledge.*` or `ingestion.*` **[Verified, updated for 11A]**. **Actual Phase 8/9 structure the builder was written against [Verified from `scripts/run_incident_analysis.py` and `incident_001/analysis/*.json`]:** both outputs are plain dictionaries with no Pydantic model (section 4.3 still stands). **Query-builder behaviour [Verified by tests]:**
- One query per finding. Components, in fixed order, each recording its origin path and basis: vulnerability type, root cause, affected component (basis `inferred_hypothesis`, or `confirmed_finding` only if `status == "confirmed"` exactly), observed-evidence descriptions (claim statements citing the finding's evidence IDs; the timeline `action` as fallback; basis `observed_evidence`), rationale, then each evidence gap (basis `evidence_gap`).
- Placeholders Phase 9 emits (`"Not confirmed from the available evidence."`, `"Undetermined from request evidence alone."`, `"unknown"`, `None`) are recognised by whole-word leading phrases and dropped. A finding with no informative subject produces **no query** and is listed as skipped (so `insufficient_evidence` boilerplate never becomes a query).
- A hypothesis stays a hypothesis: `IncidentQuery.finding_status` is copied verbatim, `is_confirmed` is False unless the status is exactly `"confirmed"`, and `RESULT_MEANING` states that retrieved items are reference knowledge that neither confirm nor refute the hypothesis.
- Evidence IDs (for example `nginx-19`) are removed from the text and kept as metadata. Raw percent-encoded attack payloads are deliberately **not** copied into queries (design choice). The LLM narrative is not a query source (model-written text). Explicit identifiers stated by the analysis itself (`CWE-89` in Phase 9's `vulnerability_type`) remain in the text; they are the analysis's hypothesis, not an answer key.
- Missing, null or empty optional fields are skipped without inventing text; wrongly typed fields raise `QueryBuildError`; a reconstruction for another incident is refused; overlong input omits the lowest-priority components and lists them in `omitted_fields`.
- Real `incident_001` artifacts yield exactly one query: status `hypothesis_not_confirmed`, evidence `application-4` / `nginx-19`, phrase `"sql injection"`, text containing `CWE-89`, no placeholder text.

**Runtime queries versus evaluation answers [Verified by tests]:**
1. `retrieval/query_builder.py` imports nothing from `retrieval/evaluation.py` and never references the benchmark; `retrieval/evaluation.py` never imports the builder (AST checks).
2. The builder reads only the documented fields, and `ground_truth`/answer-key field names (`FORBIDDEN_INPUT_KEYS`) in the input dictionaries are **refused with `ForbiddenQueryInputError`**, not ignored. The real nested `validation.ground_truth_used: false` flag is allowed and never read.

**Benchmark and methodology.** `mitre-subset-retrieval-benchmark-v1`: **22 questions** (12 `descriptive` everyday-wording, 10 `terminology`), each with a stable ID (`RB-001..022`), the question, an investigative task, 1–3 expected `doc_id`s and a rationale. ### 3.6 Phase 11 Milestone 11B: keyword-retrieval hardening, benchmark v2 and architecture lock **[Verified: code read, tests run, real archives used, 2026-10-16]**

**Scope.** Harden the keyword baseline, strengthen the benchmark and write down the dual-lane design **before** any embeddings. Implementation, testing and integration are separate: implemented and tested, **not integrated** with Phase 8/9 code. No package was installed. The schema, chunker, store, ingestion adapters, manifest, archives, `PROJECT_SPEC.md`, the Cursor rule and Phase 8/9 logic were not modified (verified by file times against the first 11B file). Nothing was staged, committed or pushed.

**Architecture decisions recorded (module docstring of `retrieval/lanes.py`; decisions, not implementations).**
- **A. Two knowledge-type lanes**, as `doc_type` filters over the one existing corpus: weakness (CWE) and attack pattern (CAPEC). No separate stores. `Lane`, `WEAKNESS_LANE`, `ATTACK_PATTERN_LANE`, `LANES` and `lane_query()` implement only the filter mechanism (tested: a lane never returns the other lane, both lanes never duplicate a document).
- **B. One shared general-purpose embedding model** for both lanes. Selection requirements are recorded as data (`EMBEDDING_MODEL_REQUIREMENTS`: local execution, licence, dimensions and max tokens against chunks of up to 1200 characters, pinned revision, CPU-only resources, no fine-tuning, evaluation against the frozen FTS5 baseline). **No model was chosen or installed.**
- **C. Source-level Reciprocal Rank Fusion, specified only.** `rrf(d) = sum over lanes of 1/(k + rank_lane(d))`; `RRF_DEFAULT_K = 60`, `RRF_MIN_K = 1`. Deterministic tie-break: higher fused score, then smaller best lane rank, then lane order (weakness before attack pattern), then `doc_id`. A fused item must keep its identity, provenance, per-lane rank and raw score, fused score and `k`. **Caveat written into the specification:** because the lanes are disjoint by `doc_type`, a document appears in only one lane, so RRF cannot reward cross-list agreement and reduces to rank interleaving. It must therefore be measured against a single unfiltered query before it is trusted. No fusion function exists (a test checks that none was added).
- **D. CVE/NVD deferred.** **E. No fine-tuning, no new packages.**

**Query-handling changes: `retrieval/fts5_v2.py`, `Fts5RetrieverV2` (`fts5-bm25-v2`).** The 11A retriever (`fts5-bm25-v1`, `retrieval/fts5.py`) is untouched, so old and new run side by side.
- Text is normalised with NFKC, every Unicode dash becomes `-`, invisible format characters are removed (zero-width space becomes a space). Identifiers (`CWE-89`, `cwe 89`, `CAPEC_66`, with any dash) become one canonical phrase `"CWE-89"` (a plain hyphen is never an FTS5 minus). `CWE89` is deliberately not guessed. Balanced straight or curly quotes become exact phrases; hyphenated compounds become adjacent-word phrases plus their words; repeated terms collapse; FTS5 operators are data, never syntax (parameterised search only). Priority when the 1000-character limit is hit: identifiers, explicit phrases, quoted spans, compounds, words (cut from the end).
- **Nothing is silently dropped:** a new `RetrievalResult.query_notes` field lists rewritten identifiers, normalisations, ignored low-content words, an unbalanced quote, cut terms and a low-information flag; dropped terms also appear in `dropped_terms`. Nothing searchable raises `InvalidRetrievalQueryError` (typed, never an empty result). A one-word query runs but is flagged (`LOW_INFORMATION_PREFIX`). Quoting is a boost, not a guarantee of rank 1 (terms are OR-ed).

The document score is the sum of its best two chunk scores (`aggregation="top2_sum"`, the default) instead of the best chunk only. The ablation `Fts5RetrieverV2(store, aggregation="best_chunk")` (`fts5-bm25-v2-bestchunk`) isolates it. Ties break by `doc_id`. The `possibly_incomplete` window rule of 11A is kept (the lane filter still runs after the store's 100-chunk window).
- A pruning-by-document-frequency idea was tried on development questions only, gave mixed results and was **not adopted**. Two generic words ("security problem") are deliberately **not** detected as low-information, to avoid tuning to unseen cases.

**Existing draft schemas.** `ValidationCheck` / `ValidationResult` in `evidence/schema.py` were inspected and **not reused and not modified**: `ValidationResult.passed: bool` with free-string `before_status` / `after_status` cannot separate "no check ran" from "the objective was not observed" (a bare boolean invites exactly that conflation), they carry no execution, scope, attestation or provenance fields, and nothing in the repository consumes them (they are referenced only inside the unused `SecurityAssessment` stub). **Status model (exact semantics).** `not_validated`: no check was attempted because an INPUT precondition is unmet (no usable plan, unknown or ineligible scenario, remediation application not attested). `blocked`: every input precondition is met but execution is prohibited (scope policy denied, or live execution does not exist). `inconclusive`: a check was attempted and nothing can be concluded (`lab_unreachable`, `timeout`, `unexpected_response`, `control_check_failed`, `evidence_insufficient`, `lab_state_unknown`). `objective_achieved`: a completed check observed the original objective succeed in the tested lab state. `objective_not_observed`: a completed check did not observe it **under the tested conditions only**. Each status has its own reason codes (`REASONS_BY_STATUS`; a code belongs to exactly one status) and the report refuses any other pairing. Construction also refuses: a conclusive result with no attempted or completed check, no evidence, no known tested lab state or an unevaluated oracle condition; a post-remediation result without an attested application; an executed check without a scope permission, satisfied preconditions or a verified lab identity; and any `not_validated` / `blocked` report that carries execution metadata, evidence, a tested state or condition results. A timeout or missing lab can only be `inconclusive`. Constant markers can never be true: `remediation_effectiveness_proven`, `general_security_guarantee`, `ground_truth_used`, `llm_used`, `remediation.applied_by_phase13`, a proposal's `executed`, and `application.verified_by_phase13`. There is no numeric score, probability or confidence field.

**What Phase 13A can produce.** Only `not_validated` or `blocked`. Preconditions are checked in a fixed order and the first unmet one is the primary reason: `plan_usable`, `incident_matches_plan`, `scenario_known`, `scenario_eligible`, `remediation_application_attested` (all -> `not_validated`), then `scope_conditions_met` and `live_execution_available` (-> `blocked`). Later preconditions that cannot be judged because an earlier one failed are listed as `evaluated: false` (unmet, never satisfied). The most advanced outcome possible is `blocked` / `execution_not_implemented_phase_13a`, even with an approved scenario, an approved lab, an independent identity, an operator authorization and `execution_enabled=True` (a test pins this). Two independent locks: the policy denies by default, and the orchestrator refuses to execute whatever the policy says (`LIVE_EXECUTION_IMPLEMENTED = False`; the reported `execution_permitted` is `False` unless this build could act on it).

**Phase 12 handling.** `intake_plan` accepts a `RemediationPlanResult`, its stored `to_dict()` form, or a bare `RemediationPlan`; it re-validates the plan with the real Phase 12 model (an instance built with `model_construct` is re-checked). Missing -> `remediation_plan_missing`; wrong type, unknown status, a rejected/failed result that carries a plan, a planned result without a valid plan or a passed validation, an insufficient result that carries proposals, mismatched incident or finding, duplicate proposal ids -> `remediation_plan_malformed`; `rejected_invalid_response` / `rejected_grounding` -> `remediation_plan_rejected`; `llm_error` -> `remediation_plan_unavailable`; `not_planned_insufficient_context` / `model_declared_insufficient` -> `remediation_plan_insufficient_context`. incident_NNN/ raw evidence (Phase 3 package)

### 4.2 Contracts to preserve

- **`EvidenceEvent`** and **`AttackGraph`** (`GraphNode`, `GraphEdge`) are **tested Pydantic models** in `evidence/schema.py`. Keep `basis` (`observed`/`configured`), `evidence_ids` and `source_artifacts`. The GNN encoders (`NODE_TYPES`, `EDGE_TYPES`, feature dimensions) depend on them.
- **`EvidenceExtraction`** (`extra="forbid"`, exactly seven keys) and the reference checks in `EvidenceExtractionAgent._validate_references`.
- **`IncidentEvidenceContext` / `EvidenceContextBuilder`**: never expose `ground_truth/`.
- **`LLMClient.generate(system_prompt, user_prompt, response_format)`** (`llm/base.py`).
- `normalized/events.jsonl` as the handoff file; event IDs such as `nginx-19`, `application-4`; `attributes["source_event_ids"]` and `["evidence_sources"]`.
- Incident naming `incident_NNN` and the two directory layouts (legacy `docker/*_after_attack.json`; current `configs/containers/*.json` + `network/autoshield_net.json`).

### 4.3 Phase 8 and Phase 9 outputs **[Verified from `incident_001/analysis/`]**

Both phases currently emit **plain JSON dictionaries** with `schema_version: "1.0"`; there is no Pydantic model for either.

- `incident_reconstruction.json` top-level keys: `schema_version`, `incident_id`, `agent`, `created_at_utc`, `evidence_summary`, `timeline`, `event_correlations`, `correlation_policy`, `claims`, `graph_relationships` (`observed`, `configured_only`, `request_level_relationships_for_suspicious_indicators`), `attack_chain_assessment`, `unconfirmed_stages`.
- `root_cause_analysis.json` top-level keys: `schema_version`, `incident_id`, `agent`, `created_at_utc`, `input_reconstruction`, `findings`, `validation`. Each entry in `findings` contains `status`, `root_cause`, `affected_component`, `vulnerability_type`, `supporting_evidence_ids`, `confidence`, `rationale` and `evidence_needed_to_confirm` (the evidence required to confirm the hypothesis).
- For `incident_001` the finding is `hypothesis_not_confirmed`, vulnerability type "potential_sql_injection (CWE-89 hypothesis)", confidence 0.55, supporting events `application-4` and `nginx-19`.
- **Component identification is weak**: `affected_component` is hard-coded to "Undetermined from request evidence alone." when an indicator exists, and `None` otherwise.
- **Vulnerability coverage is narrow**: the heuristic (`is_sqli_like`) recognises SQL-injection-like text only.

### 4.4 Unused schema stubs

`AttackReconstruction`, `Remediation`, `RemediationChange`, `ValidationCheck`, `ValidationResult`, `JudgeDecision`, `RiskAssessment`, `FeatureImportance`, `ExplainabilityResult` and `SecurityAssessment` in `evidence/schema.py` are referenced nowhere else in the repository. In particular, `AttackReconstruction` and `Remediation` **do not match** the existing Phase 8/9 JSON structures (e.g. `AttackReconstruction.root_cause` is a string, whereas the real output is a `findings` list). They should be treated as drafts, not stable contracts.
